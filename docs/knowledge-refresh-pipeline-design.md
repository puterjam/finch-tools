# 知识库目录刷新链路优化设计

日期：2026-11-04

状态：第一步缓存先返回、第二步目录分批发现与 SQL 清单分页已实施并验证；持久内容任务队列尚未实施。实施范围、性能数据、排序规则差异及未验证边界见 [第一步验证记录](knowledge-refresh-step1-verification.md) 和 [第二步验证记录](knowledge-refresh-step2-verification.md)。下方「现有实现」表保留设计时的源码证据，不应当作本次交付后的逐行描述；本次不代表大目录性能问题已全部解决。

## 一、结论与设计底线

**文件能否显示，由目录清单 SQL 决定；内容能否检索，由内容／向量索引决定。两者不能互相等待。**

用户点击刷新后，已有资料不得变成空列表。新目录应边发现边显示，不必等待整个目录遍历结束，更不能等待 PDF／Office／图片处理或向量引擎就绪。

必须区分三个动作：

1. **浏览目录**：查询本机目录清单 SQL，得到文件、目录、排序、计数和上次已知状态。
2. **刷新目录**：枚举文件系统，增量更新清单和元数据，识别新增／变化／疑似移除的文件。
3. **更新内容索引**：后台提取文字、计算内容哈希、切块和写向量；完成后提交可检索版本。

“显示文件”不等于“内容已索引”。“扫描完成”也不能被用来暗示所有内容索引已经完成。

所以，当前的“增量”主要是**内容按文件分批处理与部分结果逐步可检索**，不是完整的“目录清单增量入库 + SQL 直接分页 + 后台内容索引”。之前对完成事件和分页偏移的修复仍需保留，但不能代替这次架构解耦。

## 三、目标链路

```text
进入库 / 切换目录
  └─ 本机 SQL 清单分页 → 立即显示缓存文件与上次已知状态
       └─ 可选后台核验状态 → 只更新对应行，不阻塞分页

点击刷新
  ├─ 保留当前列表与计数，显示轻量刷新状态
  └─ 确认根目录可用、库身份未变
       └─ 分批枚举目录
            ├─ 短 SQL 事务：upsert 本批目录、文件及元数据
            ├─ 清单变更事件：更新可见行、可见计数
            └─ 新增／变化文件 → 持久内容索引任务队列

后台内容索引队列
  └─ 提取 / 哈希 / 切块 / 写向量
       └─ 核验任务仍对应当前文件版本
            └─ 短 SQL 事务提交可检索版本 → 更新单行状态

完整目录枚举成功
  └─ 根身份复核、访问范围复核
       └─ 确认删除对账；目录刷新完成
            └─ 内容索引队列可以仍在继续
```

### 3.1 清单先显示，不等待状态核验

分页接口只查询 SQL，不做以下动作：

- 加载 LanceDB／AnyDoc／OCR。
- 计算文件哈希。
- 按文件调用向量 `countRows()`。
- 对全库或本页逐个读取远端文件元数据。
- 等待正在执行的内容提取或向量写入。

文件名、相对路径、类型、大小、修改时间、排序键、计数和上次索引状态，均来自清单 SQL。

首次遇到未知状态，显示“待索引／待核验”；不能为了展示“已索引”把列表卡住，也不能仅因为 SQL 有记录就虚构向量覆盖完整。

### 3.2 目录分批入库，不等待整棵树

枚举过程按**条目数或时间窗口**提交，例如最多 200 条或约 100–250ms 产生一批；这些是初始调参范围，不是已测性能结论。

- 发现普通文件即可写入路径和类型；暂未取得的大小／时间为未知，不阻塞显示。
- 文件元数据查询使用有上限的并发；SMB 使用更低的并发。
- 不递归收集整个目录树后再一次性插入。
- 不每次把全部正常文件重置为 pending。
- 新批次只 upsert 变化行，不删除／重插整张清单。
- 开始刷新不清空上一轮数据；尚未重新走到的旧文件保留显示。
- 新库尚未枚举完成时显示“已发现 N 份”，而不是把 N 冒充最终总数。

不能承诺在文件系统尚未返回数据时瞬间列完一个全新的巨大目录，但可以保证**已有缓存立即可看，新发现数据持续可见**。

## 四、数据模型与真实增量

### 4.1 独立的文件清单

新增独立清单表，不再把 `documents` 与 `source_issues` 在内存拼接后当作完整文件列表。

建议表的职责：

| 表 | 职责 |
|---|---|
| `source_files` | 所有已发现文件的稳定 file_id、path_key、relative_path、目录、类型、大小、mtime/ctime、元数据版本、上次发现轮次 |
| `source_directories` | 已发现目录、父子关系、枚举状态、最近成功扫描轮次 |
| `scan_runs` | 本次根身份、扫描轮次、发现进度、成功／中断／离线、可安全对账的范围 |
| `index_jobs` | 待处理文件及其源版本、优先级、排队／运行／失败／暂停状态、重试与租约 |
| 原 `documents` / passages | 已提交的可检索内容版本，继续与目录清单分离 |

清单中的 file_id 必须在“待索引 → 已索引 → 更新失败”之间稳定。不能因为内容索引生成了新的 document_id 就把它当成另一份文件。

每个库使用自己的索引数据库；任务还须携带稳定的库身份和源版本，不能仅凭当前盘符或当前会话判断归属。Windows 路径大小写去重继续遵循现有规则。

### 4.2 元数据快筛与内容校验分开

默认目录刷新：

1. 比较 size、mtime、ctime，必要时结合可用的文件身份信息。
2. 元数据有变化或没有可检索版本，入内容任务队列。
3. 元数据未变化，不在目录刷新链路重新哈希或检查向量。
4. 历史失败、未完成任务依据重试策略继续处理，不把整个库重新排队。

**元数据相同不能保证内容完全相同。** 因此不能删除现有内容哈希和一致性保护；应把强校验放入后台核验任务或显式深度校验，而不是偷偷宣称元数据快筛等价于完整校验。首次升级没有可信快照的文件，允许后台建立基线，不阻塞目录可见。

### 4.3 SQL 排序分页

- 所有列表排序改为 SQL 索引查询，不再对全集 `readMetadata()` 后 JS 排序。
- 列表与计数使用相同筛选条件和一致的清单版本。
- 为目录、类型、修改时间、大小、最近索引时间等常用排序建立组合索引，并以稳定 file_id 作最终排序键。
- 大目录采用游标／锚点范围查询，不扫描并构造全集数组。
- 目录子树查询必须正确处理路径分隔与通配符转义，不把相似目录名前缀当作子目录。
- 目录计数做批量／增量维护，不能每次逐文件遍历所有祖先。

保留现有语义：默认“全部资料”包含异常并按文件去重；普通目录和标签排除异常但保留正常 pending；“未索引／异常”独立筛选。开启“隐藏不支持的文件”后，可见列表和计数同步过滤，不删除清单或原文件。

## 五、内容索引是独立后台队列

### 5.1 独立调度，不持有清单读写队列

当前不能只把 `indexStatus()` 改成一个不 await 的 Promise 就宣布解耦完成。清单读、清单短事务、内容任务与向量写入必须分开调度。

- 目录发现优先，内容任务受控并发，避免抢占整个磁盘／网络。
- 取消逐文件固定 25ms 的调度方式，改为批次／耗时预算驱动的协作式让出与背压；不能靠单纯把并发拉满换速度。基准测试必须同时覆盖真实默认配置，不能只跑 `yieldMs: 0` 的测试路径。
- SQL 写事务内不得等待 AnyDoc、OCR、文件哈希、模型下载或 LanceDB 写入。
- 原生向量引擎仍需序列化的部分留在独立索引队列，不让目录分页等待这把锁。
- 任务去重键为“库身份 + file_id + 源版本”。相同版本只排一次；变化文件替换过时的待执行任务。
- 向量引擎不可用：文件照常列出，内容任务显示排队／失败，不能让目录显示为空。
- 暂停、重启后保留任务状态。关闭 App View 不删除队列；切库按既有要求中断旧库执行，旧库待办保留供以后继续。

### 5.2 提交一致性与状态真实性

更新文件时保留旧的已提交内容，直到新版本完成。流程为：

1. 领取任务，固定库身份、file_id、source_revision。
2. 提取／哈希／写入新的向量版本，保留现有源文件变动校验。
3. 确认仍是同一库、同一文件版本，任务没有被取消或替代。
4. 确认该内容版本的向量覆盖完整。
5. 在短 SQL 事务里，以版本条件提交 document 的可检索版本和对应状态。
6. 过时版本不提交到清单；孤立向量稍后清理。

“已索引”来自已经成功提交且有覆盖证据的版本，不来自“documents 有一行”或“mtime 没变”。无法证明当前覆盖时显示待核验；也可以明确展示“上次已索引”，但不能冒充刚刚实时核验过。

实际检索仍只接受 SQL 已提交的内容版本。发现源文件变化时标记过期，不能把旧内容当成新版本；失败时保留旧版本及错误状态。

### 5.3 状态核验不阻塞页面

状态核验作为独立、低优先级任务：

- 优先核验当前可见文件，不核验全库才回首屏。
- 能批量查询向量覆盖时按批查询，不逐文件同步 `countRows()`。
- 结果带库会话版本、file_id、source_revision、status_revision；前端拒收迟到结果。
- 单行 patch，不触发全列表 reset。
- 原生调用不可立即中断时，只让调用者退出；底层调用结束后再释放句柄，保留现有安全收尾机制。

## 六、界面刷新协议：先保留，再替换／补丁

### 6.1 同库刷新绝不先清空

同一知识库、同一筛选内的刷新：

- 保留当前 docs、总数、滚动位置和可操作行。
- 可以显示“正在刷新目录／已发现 N 份”，但不把总数临时改成 0。
- 新快照准备好后再原子替换可见窗口，或应用有版本的增删改补丁。
- 旧请求迟到不能覆盖新快照。
- 清单刷新失败，保留当前快照并说明不可访问，不换成空态。
- `total=0` 必须是**有效清单查询确认的零条**，不能是读取失败／尚未完成的占位值。

跨库切换则必须立即隔离旧库数据，不把旧库文件伪装成新库缓存；优先读取新库自己的本机 SQL。没有该库缓存时显示发现进度，而不是假装已经确认空库。

### 6.2 分开四类事件

| 事件 | 职责 |
|---|---|
| `catalog.batch` | 已提交清单变更、变更范围、SQL 清单版本与计数 |
| `catalog.finished` / `catalog.failed` | 本次目录刷新结束／中断／失败，不代表内容任务完成 |
| `index.file.changed` | 单个文件的排队、处理中、已提交、失败或待核验状态 |
| `index.queue.changed` | 当前库待处理／运行／暂停数量，供轻量进度显示 |

刷新事件不再复用“任何 changed 都 resetPage”的宽泛协议。每类事件都带稳定库身份与选择会话版本，旧库事件不得串入新库。

前端不对每个文件、每次状态变化重新拉全量清单／标签／目录树。清单变更合并推送，初始按 100–250ms 级别合并；内容状态只 patch 对应行。最终事件做一次有限范围对账，不能再触发全库实时状态检查。

### 6.3 分页与阅读锚点

- 少于一页的库，每次有效刷新都显示全部文件；保留此前修复的“16 条不能截成后 11 条”边界。
- 大库支持向上／向下加载，靠近尾部自动补齐窗口。
- 内容不足以撑满视口时仍继续取数据，不能依赖用户先滚动才发现漏页。
- 锚点用稳定 file_id／路径身份，不依赖临时 issue_id 或新建 document_id。
- 刷新过程中索引时间可能变化，不强迫用户追着排序跳动；以当前快照和锚点保持阅读，明确刷新到新清单版本。
- 页数据、总数、筛选必须属于一致的清单版本，防止“总数已更新、页仍来自旧版本”。

## 七、离线、取消与删除安全

### 7.1 离线不能锁住切库

- 根可用性判断与库身份探测发生在后台刷新入口，不成为读取已有本机清单的前置条件。
- 已注册远端库需持久化已验证的网络身份与本机索引定位信息。重新打开时先打开已知本机清单，再后台探测远端；不能继续先 `realpath(远端)` 才找到缓存。新库首次添加仍须验证真实目录，不能凭一个路径猜测缓存。
- 离线浏览承诺限于实际存在的本机缓存。若本地／USB 库的 `.knowledge` 随整个盘一起不可访问，且没有另存的清单快照，就只能说明暂无可读缓存，不能伪造全量文件列表。
- 网络断开时仍可以看已经缓存的文件；状态标记为“源目录暂不可访问”，大小／时间注明为缓存信息。
- 保留一次合并的根探测，不为每个可见文件重复探测网络盘映射。
- 探测有时间预算、可取消；底层系统调用晚到只丢弃其结果，不能将其继续连接到新库工作流。
- 切库不等待旧库扫描、提取、哈希或向量查询结束；旧原生句柄在后台安全释放。
- 已经确认属于网络库的挂载点，即使后来变成仍存在的空本地目录，也不能把它当成同一个在线库清空索引。需要保留／核验库的网络身份，而不只检查路径存在。

现有离线预检查只能作为刷新保护，**不能继续放在只读 SQL 分页前面**；否则远端不可访问仍会拖住列表。

### 7.2 清单代际不等于随时可以删除

本轮扫描未看到一个文件，不立即代表文件已删除。只有满足以下条件才可提交移除：

1. 本轮目标扫描范围完整成功，没有取消／断线。
2. 根目录和网络共享身份与扫描开始时一致。
3. 对应父目录／祖先范围被成功枚举，且没有落在不可访问子树内。
4. 文件在可确认的范围内缺失，或已确认格式不再支持。
5. 对账提交时再次检查库版本、任务状态和文件源版本。

扫描中断、目录权限失败、网络映射改变时，保留旧文件与内容版本。清理动作只作用于索引和清单，不删除原文件。已经明确删除的源文件应从当前清单移除，并使旧内容不可再作为当前文件被检索。

## 八、兼容与迁移

- 为现有有效索引新增清单／任务相关表，不因为这次界面优化而整库重建、清空标签或重做所有向量。
- 首次升级从 `documents`、现有异常记录和目录记录合并生成初始清单，按文件身份去重，立刻可浏览。
- 缺失的大小／时间等元数据后台补齐，不因缺列阻塞首屏。
- 新表采用独立、明确的增量迁移版本；不能随意修改当前内容索引 `user_version`，触发旧结构备份重建分支。
- 库注册信息补充远端身份与缓存定位字段；旧记录只有路径时，在线验证一次后补充，离线时不猜测共享身份，也不新建一个误认的本地空库。
- 旧的完整性保护、标签关联、移动识别和索引备份／损坏保护保留；新增迁移不得弱化原生产守卫。
- “隐藏不支持的文件”继续持久化；切换开关只是 SQL 筛选，不修改历史原文件或丢弃异常记录。

## 九、实施顺序

### 第一步：解除列表硬阻塞，先止住“刷新看不到文件”

1. 清单返回与 `indexStatus()` 解耦。
2. 读取已有清单不等待根探测、哈希、向量引擎和内容写队列；取消按文件数量线性累加的固定等待，替换为有预算的协作调度。
3. 同库刷新不清空 docs／不把总数归零；请求与快照版本严格匹配。
4. 页内状态改为后台更新，不虚构 ready。
5. 用受控屏障测试证明：向量查询／内容哈希卡住时，分页仍已返回。

此步能解决“缓存文件不可看”，但**还不能宣称大目录的首次发现已经实现增量入库**。

### 第二步：目录清单真正增量化

1. 新增并迁移 `source_files`、目录／扫描表。
2. 分批枚举、分批 SQL upsert，元数据受控并发。
3. SQL 排序分页、统一计数条件和索引。
4. 只有完整成功范围才能对账删除。
5. 首批可见不等待完整目录树，扫描期间旧文件持续可看。

### 第三步：内容索引持久队列化

1. 新增／变化文件去重入队，未变化文件不在刷新链路做强校验。
2. 独立内容写队列、短 SQL 提交、源版本 CAS。
3. 中断／恢复／重启／切库正确归属；后台强校验保障内容一致性。
4. 合并事件、可见行优先，减少刷新与任务互相放大的工作量。

### 第四步：大库与网络盘压测后交付

不能只跑 16 个文件的 UI 用例就宣布解决大库性能。完成下方矩阵，并在报告中区分目标、实测值和未验证平台。

## 十、验收与性能观测

### 硬性功能验收

- 已有 10,000／100,000 条缓存文件时，打开／刷新期间文件列表不被替换为空态。
- 目录清单分页路径上：**0 次内容哈希、0 次提取、0 次向量引擎调用、0 次逐文件远端元数据读取**。
- 向量引擎尚未下载、阻塞或失败，目录和计数仍能查询。
- 控制枚举屏障：第一批已写入且可见时，后续目录仍未枚举完成。
- 阻塞内容任务后，清单还能入库、分页、切换目录；不依赖延长超时通过测试。
- 同库刷新先返回慢旧请求、后返回快新请求，以及反向乱序，都不会归零或覆盖新数据。
- 16 条完整显示 16 条；57 条／多页／高视口／索引时间重排均无遗漏或重复。
- 新增、修改、重命名、删除、空文件、不支持格式、失败恢复和过滤计数一致。
- 全库无变化刷新不会重新提取全文，也不在刷新链路重新校验每个文件的向量行数。
- 元数据相同但内容被特殊方式改变的情况，不能假定已通过强校验；由后台校验发现并更新。
- 断盘、空挂载点、映射盘换共享、权限不足、扫描取消均不得误删；旧库任务不可污染新库。
- 用户暂停后不偷偷恢复；应用／App View 重开能继续读取清单并遵守持久暂停状态。
- SQL 迁移保留旧标签、已有内容版本与有效索引，不自动替换损坏或未来版本数据库。

### 性能目标（待基准验证，不是完成承诺）

- 有缓存首屏以约 200ms 级别为优化目标，记录实际 P50／P95；具体目标需在固定机器和数据集上校准。
- 已完成 SQL 批次应尽快推送到界面，初始以数百毫秒级为事件合并目标。
- 新库完整扫描时间取决于文件系统返回速度，不承诺大库／SMB 一次完整扫描瞬间完成。
- 使用本机 10k、100k，深目录／宽目录、混合大文件，以及真实 SMB 高延迟样本分别测量。
- 记录首屏耗时、首批发现耗时、清单批次提交时间、目录遍历时间、SQL 查询与计数时间、内容队列耗时、取消响应时间和远端 I/O 次数。
- 报告必须将“目录可见速度”与“全部内容完成索引的时间”分开；不能用小文件先出一条检索结果来证明目录刷新已经很快。

## 十一、此次不采用的补丁

- 不增加一个完成后刷新就当作性能修复。
- 不把 loading 动画换成别的文案掩盖等待。
- 不因为查询慢就清空当前列表／把失败返回成 `total=0`。
- 不把文件系统元数据快筛冒充内容完整校验。
- 不通过减少真实检索范围、假报已索引或放宽断盘删除守卫来换速度。
- 不在本次设计确认前继续发布一个声称已完成架构优化的安装包。
